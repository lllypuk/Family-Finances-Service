## D-01 — `make docker-up` не запускается

**Приоритет: P0.** — ✅ **Закрыта** (задача 10 плана).

`docker/docker-compose.yml` (именно его используют цели `docker-up`, `docker-up-d`,
`docker-build`) передаёт `SESSION_SECRET`, но **не передаёт `CSRF_SECRET`**, при этом
`ENVIRONMENT` по умолчанию `production`. Валидация конфига это отвергает.

Проверено напрямую:

```bash
ENVIRONMENT=production SESSION_SECRET=some-real-secret ./family-budget-service
# 2026/08/16 21:13:31 Failed to create application:
#   invalid configuration: CSRF secret must be changed in production
```

Контейнер будет падать в рестарт-петле. Задокументированный путь «`make docker-up`»
не работает из коробки.

Та же мина в `deploy/docker-compose.prod.yml`, `.nginx.yml`, `.caddy.yml`: там
написано `CSRF_SECRET=${CSRF_SECRET:-}` — пустая строка, а `getEnv` считает пустую
строку отсутствием значения и подставляет плейсхолдер. Спасает только `install.sh`,
который генерирует секрет и пишет его в `.env` (строки 130, 211). То есть скриптовый
путь рабочий, а ручной `docker compose up` — нет.

**Что делать:** добавить `CSRF_SECRET` в `docker/docker-compose.yml` по образцу
`SESSION_SECRET` (с `:?` — чтобы падать понятно, а не молча), и заменить `:-` на `:?`
в остальных compose-файлах.

### ✅ Что сделано

Во всех пяти файлах оба секрета объявлены как
``${VAR:?VAR is required - generate one with `openssl rand -base64 32`}``.
Без секретов `docker compose up` завершается кодом 1 ещё до создания контейнера.
`CSRF_SECRET` добавлен в корневой `.env.example` и в
`deploy/.env.production.example`.

Три следствия, о которых стоит знать:

- **Сообщение об ошибке в `:?` не может содержать `: `** — compose парсит YAML до
  интерполяции и валится на `mapping values are not allowed`. Отсюда тире вместо
  двоеточия в формулировке.
- **`.env` живёт в корне репозитория**, как и учит `README.md`. `env_file` тут не
  помогает: он наполняет окружение контейнера, а падает *интерполяция*, которая
  читает только shell-окружение и `.env` из project directory. Поэтому compose
  вызывается с `--project-directory .` (прописано в `Makefile`, переменная
  `DOCKER_COMPOSE`).
- **`make compose-config`** валидирует все пять файлов и запускается в CI, чтобы
  D-01 не воспроизвёлся при следующей правке.

➕ Попутно во всех пяти файлах и в самом `docker/Dockerfile` починен healthcheck:
`wget --spider` шлёт **HEAD**, а зарегистрирован только `GET /health` — HEAD
проваливался в редирект `/login` ⇄ `/setup`, wget выходил с кодом 8 и контейнер
навсегда оставался `unhealthy`. Теперь `wget -O /dev/null`; контейнер становится
`healthy` примерно за 9 секунд.

## D-02 — Docker-образ никогда не публиковался

**Приоритет: P0.** — ✅ **Закрыта** (задача 11 плана) — выбран вариант «собирать
на месте», тег так и не поставлен.

```bash
git tag | wc -l        # 0
gh release list        # пусто
```

`.github/workflows/docker.yml` срабатывает только на теги `v*.*.*`, на публикацию
релиза или вручную. Тегов нет ни одного → в GHCR ничего нет.

При этом **все** production-конфиги ссылаются на несуществующий образ:

```yaml
image: ghcr.io/lllypuk/family-finances-service:latest   # prod, minimal, nginx, caddy
```

`docker compose up` завершится ошибкой `manifest unknown`.

**Что делать:** поставить первый тег (`v0.1.0`) и дождаться сборки, либо — что
проще для домашнего сервера — собирать образ на месте из исходников (`build:` вместо
`image:`), как это уже делает `docker/docker-compose.yml`.

### ✅ Что сделано — выбран второй путь

Все четыре `deploy/*.yml` переведены на
`build: {context: ${BUILD_CONTEXT:-..}, dockerfile: docker/Dockerfile}`; `image:`
намеренно не задан, чтобы `docker compose pull` не ходил в реестр за
несуществующим образом. Контекст сделан переменной, а не фиксированным `..`:
из репозитория работает значение по умолчанию, а `install.sh` кладёт compose в
`/opt/family-budget`, где `..` — это `/opt`.

`install.sh` теперь клонирует репозиторий в `$INSTALL_DIR/src`, пишет
`BUILD_CONTEXT=./src` в `config/.env` и делает `build` вместо `pull`; при
необходимости сам ставит `git` (`install_git()` в `lib/common.sh`).
`upgrade.sh` переведён с тегов образа на git-ref: `--version` принимает
тег/ветку/коммит (`latest` → `main`), `version.txt` хранит SHA, откат — checkout
этого SHA и пересборка.

### ⚠️ Тег `v0.1.0` так и не поставлен — и просто так его ставить нельзя

Публикация образа осталась незакрытой сознательно, но в `docker.yml` есть
дефект, который надо починить **до** первого тега, иначе релизная сборка упадёт:

```yaml
# .github/workflows/docker.yml
- name: Build and push Docker image
  uses: docker/build-push-action@v6
  with:
    context: .          # ← file: не указан, значит ./Dockerfile
```

`docker/build-push-action` при отсутствии `file:` берёт `{context}/Dockerfile`,
а Dockerfile в этом репозитории лежит в `docker/Dockerfile` — файла `./Dockerfile`
нет. Пуш тега `v*.*.*` запустит workflow, и шаг сборки провалится на
«failed to read dockerfile». Нужно добавить `file: docker/Dockerfile`.

Что тег запускает, если workflow починить: логин в `ghcr.io`, multi-arch сборка
(`linux/amd64,linux/arm64`) с пушем, теги `{{version}}`, `{{major}}.{{minor}}`,
`{{major}}` и `latest`, скан Trivy с выгрузкой SARIF в Security tab,
**жёсткая проверка размера образа — падение при > 50 МБ** (проверить заранее:
образ несёт бинарник, шаблоны, статику и миграции) и smoke-тест
`docker run --rm <image> -health-check` (флаг существует, `cmd/server/main.go:24`).

Постановка тега — действие владельца репозитория, наружу; в рамках плана оно не
выполнялось.

## D-03 — Несоответствие UID в prod-конфиге

**Приоритет: P2.** Проверить на стенде. — ✅ **Закрыта** (задача 11 плана).

`docker/Dockerfile` создаёт `/data` с владельцем `nobody` (65534) и запускает процесс
от него. А `deploy/docker-compose.prod.yml` переопределяет пользователя:

```yaml
user: "1000:1000"
volumes:
  - ./data:/data
```

Процесс от 1000:1000 пишет в примонтированный с хоста `./data`. Права зависят от
владельца каталога на хосте — если он создан root'ом, SQLite не сможет открыть базу
на запись. Симптом будет невнятным: ошибка открытия БД при старте.

**Что делать:** согласовать UID между Dockerfile и compose и создавать каталог с
нужным владельцем в `install.sh`.

### ✅ Что сделано

Согласовано в сторону **1000**, а не 65534: `docker/Dockerfile` заводит
пользователя `app` = 1000:1000 (`USER 1000:1000`) и отдаёт ему `/data`,
`/backups`, `/logs`; `prod.yml` со своим `user: "1000:1000"` совпал с образом без
правок. `install.sh` делает `chown 1000:1000` на смонтированные каталоги **после**
общего `chown -R $APP_USER` — системный `$APP_USER` имеет UID < 1000 и для
bind-mount не годится.

Проверено вживую: `id` внутри контейнера — `uid=1000(app) gid=1000(app)`,
SQLite создаёт `budget.db` на bind-mount, `/health` → 200.

`docs/tasks/` в `deploy/` не осталось (`grep -rn "docs/tasks" deploy/` — пусто).
Ссылки на `.memory_bank/` в `README.md` переведены на `docs/`.

### ⬜ Что осталось

`.claude/skills/memory-update/SKILL.md` и `.claude/skills/README.md` по-прежнему
описывают `.memory_bank/`. Это инструмент разработки, а не документация
развёртывания, — вынесено за объём плана.

## Что в деплое сделано хорошо

Инфраструктура — сильная сторона проекта, 2438 строк осмысленных скриптов:

- **Три сценария развёртывания:** Docker+nginx, Docker+Caddy (автоматический HTTPS),
  нативный systemd без Docker.
- **`install.sh`** генерирует секреты, ставит Docker, настраивает firewall,
  раскладывает `.env` — с флагами `--domain`, `--email`, `--non-interactive`.
- **`upgrade.sh`** (461 строка) с автоматическим откатом при неудаче.
- **`backup.sh`** с проверкой целостности, ежедневно в 3:00 через systemd timer.
- **`uninstall.sh`** с сохранением данных.
- **Закалка контейнера:** `cap_drop: ALL`, `no-new-privileges`, tmpfs на `/tmp`,
  непривилегированный пользователь, порт слушает только `127.0.0.1` (для проксирования).
- **fail2ban** и rate limiting в конфигах nginx/Caddy.
- **Security-заголовки** вынесены в отдельный сниппет.

Это заметно выше среднего для пет-проекта.
