# 004 — Готовность к развёртыванию на домашнем сервере

**Дата:** 16.08.2026 · **Сценарий:** self-hosted на мини-сервере с доступом по SSH

## Ресурсы: запас огромный

Измерено на работающем экземпляре:

| Параметр | Значение |
|---|---|
| Бинарник (`CGO_ENABLED=0`, `-ldflags="-w -s"`) | 25 МБ |
| RSS процесса под нагрузкой сценария | 7–11 МБ |
| База после setup + транзакция | 280 КБ |
| Ожидаемый размер образа | ~40 МБ (Alpine 3.20 + бинарник + шаблоны) |

`deploy/README.md` требует «минимум 2 ГБ RAM». Это на два порядка больше нужного —
сервис комфортно живёт в 128–256 МБ. Требование стоит понизить, оно отпугивает от
разумного железа.

Драйвер SQLite — `modernc.org/sqlite`, чистый Go, CGO не нужен. Кросс-компиляция
под ARM (Raspberry Pi, мини-ПК на ARM) работает без тулчейнов.

## D-01 — `make docker-up` не запускается {#d-01}

**Приоритет: P0.**

`docker/docker-compose.yml` (именно его используют цели `docker-up`, `docker-up-d`,
`docker-build`) передаёт `SESSION_SECRET`, но **не передаёт `CSRF_SECRET`**, при этом
`ENVIRONMENT` по умолчанию `production`. Валидация конфига это отвергает.

Проверено напрямую:

```bash
ENVIRONMENT=production SESSION_SECRET=some-real-secret ./family-budget-service
# 2026/08/16 21:13:31 Failed to create application:
#   invalid configuration: CSRF secret must be changed in production
```

Контейнер будет падать в рестарт-петле. Задокументированный путь «`make docker-up`»
не работает из коробки.

Та же мина в `deploy/docker-compose.prod.yml`, `.nginx.yml`, `.caddy.yml`: там
написано `CSRF_SECRET=${CSRF_SECRET:-}` — пустая строка, а `getEnv` считает пустую
строку отсутствием значения и подставляет плейсхолдер. Спасает только `install.sh`,
который генерирует секрет и пишет его в `.env` (строки 130, 211). То есть скриптовый
путь рабочий, а ручной `docker compose up` — нет.

**Что делать:** добавить `CSRF_SECRET` в `docker/docker-compose.yml` по образцу
`SESSION_SECRET` (с `:?` — чтобы падать понятно, а не молча), и заменить `:-` на `:?`
в остальных compose-файлах.

## D-02 — Docker-образ никогда не публиковался {#d-02}

**Приоритет: P0.**

```bash
git tag | wc -l        # 0
gh release list        # пусто
```

`.github/workflows/docker.yml` срабатывает только на теги `v*.*.*`, на публикацию
релиза или вручную. Тегов нет ни одного → в GHCR ничего нет.

При этом **все** production-конфиги ссылаются на несуществующий образ:

```yaml
image: ghcr.io/lllypuk/family-finances-service:latest   # prod, minimal, nginx, caddy
```

`docker compose up` завершится ошибкой `manifest unknown`.

**Что делать:** поставить первый тег (`v0.1.0`) и дождаться сборки, либо — что
проще для домашнего сервера — собирать образ на месте из исходников (`build:` вместо
`image:`), как это уже делает `docker/docker-compose.yml`.

## D-03 — Несоответствие UID в prod-конфиге {#d-03}

**Приоритет: P2.** Проверить на стенде.

`docker/Dockerfile` создаёт `/data` с владельцем `nobody` (65534) и запускает процесс
от него. А `deploy/docker-compose.prod.yml` переопределяет пользователя:

```yaml
user: "1000:1000"
volumes:
  - ./data:/data
```

Процесс от 1000:1000 пишет в примонтированный с хоста `./data`. Права зависят от
владельца каталога на хосте — если он создан root'ом, SQLite не сможет открыть базу
на запись. Симптом будет невнятным: ошибка открытия БД при старте.

**Что делать:** согласовать UID между Dockerfile и compose и создавать каталог с
нужным владельцем в `install.sh`.

## D-04 — Ссылки на несуществующую документацию {#d-04}

**Приоритет: P3.**

`install.sh:310` по завершении советует: *«см. docs/tasks/002-reverse-proxy-config.md»*.
Каталога `docs/tasks/` в репозитории нет. Пользователь в конце установки получает
указание на несуществующий файл.

Похожая ситуация в `CLAUDE.md` и `README.md`, которые ссылались на `.memory_bank/` —
каталог переименован в `docs/` (`CLAUDE.md` в этой сессии уже поправлен).
Скилл `.claude/skills/memory-update/SKILL.md` всё ещё указывает на `.memory_bank/`.

## Что в деплое сделано хорошо

Инфраструктура — сильная сторона проекта, 2438 строк осмысленных скриптов:

- **Три сценария развёртывания:** Docker+nginx, Docker+Caddy (автоматический HTTPS),
  нативный systemd без Docker.
- **`install.sh`** генерирует секреты, ставит Docker, настраивает firewall,
  раскладывает `.env` — с флагами `--domain`, `--email`, `--non-interactive`.
- **`upgrade.sh`** (461 строка) с автоматическим откатом при неудаче.
- **`backup.sh`** с проверкой целостности, ежедневно в 3:00 через systemd timer.
- **`uninstall.sh`** с сохранением данных.
- **Закалка контейнера:** `cap_drop: ALL`, `no-new-privileges`, tmpfs на `/tmp`,
  непривилегированный пользователь, порт слушает только `127.0.0.1` (для проксирования).
- **fail2ban** и rate limiting в конфигах nginx/Caddy.
- **Security-заголовки** вынесены в отдельный сниппет.

Это заметно выше среднего для пет-проекта.

## Порядок действий для вашего мини-сервера

**Сейчас выставлять наружу нельзя** — из-за [S-01](002-security-audit.md#s-01)
открытый API отдаст и позволит удалить все данные любому, кто дотянется до порта.

Безопасный порядок:

1. **Закрыть S-01** — аутентификация на `/api/v1`. Это единственный настоящий блокер
   безопасности.
2. **Починить D-01 и D-02** — иначе развёртывание просто не поднимется.
3. **Первый выкат — только в локальную сеть или через SSH-туннель**, без публичного
   домена. Сервис слушает `127.0.0.1:8080`, доступ — `ssh -L 8080:127.0.0.1:8080 mini`.
   Так можно пользоваться уже сейчас, ничего не выставляя в интернет.
4. Пройти setup, убедиться, что данные ходят, снять первый бэкап и **проверить
   восстановление** — бэкап без проверенного восстановления бэкапом не является.
5. Только после этого — публичный домен, Caddy (автоматический SSL, меньше ручной
   работы, чем nginx+certbot), fail2ban.
6. Настроить внешний мониторинг `/health` — с поправкой на [U-01](003-ui-ux-audit.md#u-01),
   до завершения setup эндпоинт отвечает 302.

Пункт 3 позволяет начать пользоваться сервисом уже на выходных, не дожидаясь
исправления безопасности: в локальной сети открытый API — приемлемый риск, в
интернете — нет.
