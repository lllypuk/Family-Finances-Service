# 001 — Общая оценка проекта

**Дата:** 16.08.2026 · **Коммит:** `995aebf`

## Резюме

Family Finances Service — зрелый пет-проект с инженерной культурой выше средней:
честная слоёная архитектура, 75 тестовых файлов, строгий линтер на 100+ правил,
шесть CI-пайплайнов, продуманная автоматизация развёртывания.

Главная проблема не в качестве кода, а в **расхождении между слоями**. Веб-слой
писался позже API-слоя и ушёл вперёд: у него есть аутентификация, роли, инвайты,
единая модель семьи. API-слой остался в прежнем состоянии — без аутентификации
(см. [002](002-security-audit.md#s-01)) и с незаконченной генерацией отчётов.
То же расхождение в шаблонах: макет `base.html` написан, но ни одна страница его не
использует (см. [003](003-ui-ux-audit.md#u-04)).

Это типичная болезнь роста, а не системный дефект. Лечится точечно.

## Архитектура

Слои и направление зависимостей выдержаны честно:

```
cmd/server → internal/run.go (единая точка сборки зависимостей)
                ↓
    web/ + application/handlers/     — HTTP, два интерфейса на одном Echo
                ↓
            services/                — бизнес-логика, интерфейсы репозиториев
                ↓
         infrastructure/             — реализации на SQLite
```

**Что сделано правильно:**

- **Одна точка сборки.** `internal/run.go` собирает конфиг → БД → миграции →
  репозитории → сервисы → HTTP. Читается сверху вниз, никакой магии с DI-контейнерами.
- **Интерфейсы объявлены на стороне потребителя.** `services/interfaces.go` описывает,
  что сервисам нужно от хранилища; `infrastructure` это реализует. Это правильное
  направление, а не наоборот.
- **Graceful shutdown** с таймаутом 30 секунд, корректное закрытие БД.
- **Модель одной семьи** — сознательное упрощение под self-hosted. `RequireSetup`
  ведёт новый инстанс через первичную настройку, дальше пользователи заводятся
  только по инвайтам. Для домашнего сервера это правильнее мультитенантности.
- **Миграции применяются на старте**, консолидированы в два файла. Для проекта,
  который разворачивают одной командой, это удобнее, чем цепочка из 40 миграций.
- **Тесты на in-memory SQLite** — без Docker, без сокетов, весь прогон меньше секунды.
  Это заметно лучше, чем testcontainers, и явно продумано.

**Где архитектура поехала:**

- **Дублирование контракта репозиториев.** `application/handlers/repositories.go`
  переобъявляет интерфейсы алиасами поверх `services`. Работает, но означает, что
  два слоя претендуют на владение одним контрактом.
- **Два HTTP-интерфейса с разной моделью безопасности** на одном Echo-инстансе.
  Веб защищён, API — нет. Это не архитектурное решение, а недоделка.
- **Толстые хендлеры.** `dashboard.go` — 1076 строк, `categories.go` — 954,
  `budgets.go` — 917. При заявленном правиле «хендлеры тонкие, логика в services»
  это расхождение с собственным стандартом. `report_service.go` на 1183 строки —
  кандидат на разбиение по типам отчётов.

## Качество кода

**Линтер.** `.golangci.yml` — конфиг Maratori с проектными правками: 100+ правил,
включая `gochecknoglobals`, `mnd` (запрет магических чисел), `cyclop` со средней
сложностью пакета 10.0, `sloglint` с запретом глобальных логгеров, `depguard`
(запрет `log` в пользу `log/slog`, `math/rand` в пользу `math/rand/v2`). Исключения
осмысленные и прокомментированы — видно, что их добавляли по факту, а не отключали
пачкой.

**Наблюдаемость.** Структурированное логирование через `slog` с request_id,
`/health` с плагинами проверок (SQLite подключён отдельной проверкой).

**CI.** Шесть пайплайнов: линтер, `govulncheck`, тесты с покрытием в Codecov, сборка,
проверка Docker-сборки, плюс отдельный security-workflow (CodeQL, Semgrep, TruffleHog,
OSV, Scorecard) и Dependabot. Свежие коммиты в истории — это как раз автообновления
зависимостей, механизм живой.

**Что смущает:**

- Комментарии и сообщения об ошибках смешаны: русский и английский в одних файлах.
- Заголовки страниц захардкожены по-английски в русском интерфейсе
  ([U-05](003-ui-ux-audit.md#u-05)).
- Порог покрытия в CI выставлен на 50% и при недоборе печатает `Warning`, но не
  роняет сборку. Фактически гейта нет.

## Оценка по направлениям

| Направление | Оценка | Обоснование |
|---|---|---|
| Архитектура | 8/10 | Чистые слои, единая сборка зависимостей. Минус за толстые хендлеры и дублирование контракта |
| Качество кода | 8/10 | Строгий линтер, стабильные тесты. Минус за смешение языков |
| Тестирование | 7/10 | 61.9% и быстрый прогон. Минус за замоканный рендерер, пропустивший реальные баги |
| Безопасность | 3/10 | Основы (bcrypt, cookie, CSRF, инвайты) сделаны правильно, но открытый API перевешивает всё |
| UI/UX | 5/10 | Функционально работает, но нет макета, ломается навигация, непригоден на телефоне |
| Инфраструктура деплоя | 8/10 | 2400 строк качественных скриптов. Минус за неопубликованный образ и нерабочий compose |
| Документация | 7/10 | Подробная и честная. Минус за ссылки на переименованные и несуществующие каталоги |

**Итог: крепкая основа, один блокирующий дефект.** Проект ближе к «готов», чем
кажется по списку находок: почти все проблемы локальны и чинятся точечно. Открытый
API — единственное, что действительно нельзя откладывать.
