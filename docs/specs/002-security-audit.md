## S-01 — REST API работает без аутентификации {#s-01}

**Приоритет: P0. Блокер развёртывания.**

Группа `/api/v1` регистрируется без единого middleware аутентификации.
Аутентификация есть только на веб-маршрутах (`RequireAuth` в `internal/web/web.go`),
а API-группа в `internal/application/http_server.go:152` создаётся «голой»:

```go
api := s.echo.Group("/api/v1")   // http_server.go:152 — middleware нет
users := api.Group("/users")
users.POST("", s.userHandler.CreateUser)
// ... и так все сущности
```

### Что проверено

**Чтение — полностью открыто.** Без cookie, без заголовков:

```bash
curl -s 127.0.0.1:8090/api/v1/transactions
# HTTP 200
# {"data":[{"id":"4c787b4d-…","amount":1500,"type":"expense",
#           "description":"Тестовая покупка в магазине", …}]}

curl -s 127.0.0.1:8090/api/v1/categories
# HTTP 200 — весь список категорий семьи
```

**Запись — тоже открыта.** Единственное, что стоит на пути, — CSRF middleware,
который применён глобально. Но CSRF не является аутентификацией: токен выдаётся
любому анонимному посетителю на публичной странице `/login`. Полный обход:

```bash
# 1. Берём анонимную сессию и CSRF-токен с публичной страницы входа
curl -s -c cj.txt 127.0.0.1:8090/login -o page.html
T=$(grep -oE '_token" value="[^"]*"' page.html | head -1 | sed 's/.*value="//;s/"//')

# 2. Создаём транзакцию в чужой семье
curl -s -b cj.txt -X POST 127.0.0.1:8090/api/v1/transactions \
  -H 'Content-Type: application/json' -H "X-Csrf-Token: $T" \
  -d '{"amount":99999,"type":"expense","description":"UNAUTH INJECTION", …}'
# HTTP 201 Created  ← запись без единого пароля

# 3. Удаляем чужую транзакцию
curl -s -b cj.txt -X DELETE 127.0.0.1:8090/api/v1/transactions/$TX -H "X-Csrf-Token: $T"
# HTTP 204 No Content  ← удаление без единого пароля
```

Результат: **HTTP 201 и 204 получены без аутентификации.** Любой, кто дотянется до
порта, читает всю финансовую историю семьи и может её изменить или стереть.

### Почему это важно именно сейчас

Весь смысл `deploy/` — выставить сервис наружу через reverse proxy с SSL. Ни nginx,
ни Caddy в текущих конфигах не ограничивают `/api/v1` — они проксируют всё. То есть
после развёртывания по инструкции API окажется открыт в интернет.

### Что делать

1. Ввести аутентификацию для API. Минимально приемлемо — переиспользовать сессию:
   навесить `middleware.RequireAuth()` на группу `api`. Правильно — отдельные
   API-токены, потому что сессия завязана на cookie и браузер.
2. Проверять принадлежность к семье и роль в каждом хендлере, а не только наличие сессии.
3. До выката фикса — закрыть `/api/v1` на уровне reverse proxy (`deny all`), если
   API снаружи не нужен. Это временная мера, не решение.
4. Добавить регрессионный тест: анонимный запрос к каждому методу `/api/v1` → 401.

> Отдельно: `user_id` приходит в теле запроса и принимается на веру. Даже после
> добавления аутентификации его нужно брать из сессии, иначе останется возможность
> писать данные от чужого имени.

## S-02 — CSRF-токен не привязан к пользователю {#s-02}

**Приоритет: P1.**

`internal/web/middleware/csrf.go:72` сравнивает токен из запроса с токеном в сессии.
Логика сама по себе корректна, но токен выдаётся ещё до входа в систему и **не
перевыпускается после успешного логина**. Это классическая session fixation на
CSRF-токене: значение, полученное анонимно, продолжает действовать после входа.

Именно это делает обход в S-01 таким простым.

**Что делать:** перевыпускать CSRF-токен и идентификатор сессии в момент успешной
аутентификации (`AuthHandler.Login`) и при выходе.

## S-03 — Нет защиты от перебора пароля {#s-03}

**Приоритет: P1.**

Поиск по коду не находит ни rate limiting, ни блокировки после неудачных попыток:

```bash
grep -rn "RateLimit\|Throttle" internal/ --include='*.go'   # пусто
grep -rn "attempt\|lockout" internal/web/handlers/auth.go   # пусто
```

Защита существует только во внешних конфигах: `deploy/nginx` (5 запросов/мин на
логин) и fail2ban. Из этого следуют два риска:

- Развёртывание без reverse proxy (`docker-compose.minimal.yml`, systemd на голом
  порту) остаётся полностью беззащитным.
- fail2ban разбирает логи nginx. Приложение не логирует неудачные попытки входа в
  пригодном для парсинга виде, поэтому реальная эффективность jail'а под вопросом —
  это нужно проверить отдельно на стенде.

**Что делать:** ограничение попыток в самом приложении (по IP и по email),
структурированный лог неудачных входов, экспоненциальная задержка.

## S-04 — Секреты по умолчанию срабатывают тихо {#s-04}

**Приоритет: P2.**

`internal/config.go` подставляет предсказуемые значения по умолчанию:

```go
SessionSecret: getEnv("SESSION_SECRET", "your-super-secret-session-key-change-in-production")
CSRFSecret:    getEnv("CSRF_SECRET",    "your-csrf-secret-key-change-in-production")
```

В production `Validate()` их отвергает — это правильно. Но:

- В `development` и `test` печатается предупреждение в stderr, и приложение работает
  дальше. Домашний сервер, запущенный с `ENVIRONMENT=development` (а именно так
  выглядит `docker-compose.minimal.yml`, где по умолчанию стоит
  `ENVIRONMENT=development`), получит **известный всему интернету ключ подписи сессий**.
  Подделать cookie администратора при этом тривиально.
- Проверка сравнивает с конкретной строкой-плейсхолдером. Секрет `123` её проходит.

**Что делать:** требовать `SESSION_SECRET`/`CSRF_SECRET` во всех окружениях, кроме
тестов; проверять минимальную длину и энтропию, а не равенство плейсхолдеру; убрать
`ENVIRONMENT=development` из `docker-compose.minimal.yml`.

## S-05 — `IsSetupComplete` дергает БД на каждом запросе {#s-05}

**Приоритет: P2.** Скорее устойчивость, чем безопасность.

`middleware.RequireSetup` зарегистрирован глобально (`internal/web/web.go:88`) и на
**каждый** запрос — включая каждый CSS-файл, каждую иконку — выполняет запрос в БД.
Для SQLite на домашнем сервере это переживаемо, но это бесплатный вектор нагрузки:
анонимный поток запросов к статике превращается в поток запросов к базе.

**Что делать:** кэшировать факт завершённой настройки в памяти (флаг сбрасывается
после `SetupFamily`) и исключить `/static` и `/health` из middleware — см. также
[U-01](003-ui-ux-audit.md#u-01).

## Что сделано хорошо

Чтобы картина была честной — эти вещи проверены и сделаны правильно:

- **Пароли:** bcrypt, без самодельной криптографии.
- **Cookie сессии:** `HttpOnly: true`, `SameSite: Lax`, `Secure` включается
  автоматически в production (`internal/web/middleware/session.go:39`).
- **Инвайт-токены:** криптостойкие 32 байта, срок жизни и статус отслеживаются.
- **Backup:** есть защита от path traversal и валидация имени файла, доступ только
  администратору — покрыто отдельным тестом `backup_service_security_test.go`.
- **SQL:** везде параметризованные запросы, конкатенации в запросах не найдено.
- **CI:** gosec, govulncheck, CodeQL, Semgrep, TruffleHog, OSV, Scorecard.
- **Контейнер:** непривилегированный пользователь, `cap_drop: ALL`,
  `no-new-privileges`, tmpfs на `/tmp`.

Проблема не в отсутствии культуры безопасности, а в одной конкретной дыре:
API-слой писался раньше веб-слоя и не получил аутентификацию, когда она появилась.
