## Как проводился аудит

- **Дата:** 16 августа 2026, коммит `995aebf` (ветка `main`, дерево чистое)
- **Тесты:** `go test ./...` — все пакеты зелёные; покрытие 61.9% по строкам
- **Runtime:** приложение запущено локально (`ENVIRONMENT=development`, SQLite `./data/budget.db`, порт 8090)
- **UI:** реальный Chrome через `agent-browser`, аудит доступности — axe-core 4.12.1
- **API:** проверки `curl` без сессии, с чистым cookie jar

Все находки ниже воспроизведены на живом экземпляре, а не выведены из чтения кода.
Команды воспроизведения приведены в каждом документе.

## Сводка

Проект технически крепкий: чистая слоёная архитектура, 75 тестовых файлов,
строгий линтер, продуманные скрипты развёртывания. Но **на момент аудита выставлять
его в интернет было нельзя** — REST API работал без аутентификации (проверено live:
чтение, создание и удаление чужих данных без единого пароля).

Порядок работ: сначала блокеры из 002, затем баги UI из 003, затем чистка деплоя из 004.

## Статус на 17.08.2026

План [20260816-deployment-blockers](../plans/completed/20260816-deployment-blockers.md)
(коммиты `077783b`..`63a4ea3`) закрыл **все P0** — блокеров развёртывания больше нет.
Проверено на живом сервере и на реальном `docker run`: `make test` зелёный,
`make lint` — 0 issues, покрытие 63.1% против исходных 61.9%.

Ревью фазы 1 закрыло сверх плана: `/budgets/alerts` (страница переписана под
реальную view-модель), `/users` и `/users/new` (рендерились по несуществующим
именам шаблонов), `/categories/:id` и `/categories/:id/edit`, перерисовку форм
после ошибок валидации, страницу приглашения и два HTMX-партиала категорий.
Все они отдавали 500 или обрезанный HTML, потому что рендерер писал прямо в
ответ и статус ошибки не выставлялся — теперь шаблон исполняется в буфер, а
страница ошибки уходит с настоящим кодом.
