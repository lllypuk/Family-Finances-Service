# API Standards — стандарты проектирования API

Правила, общие для всего `/api/v1`. Источник истины по конкретным роутам, схемам и кодам —
[`docs/api/openapi.yaml`](../api/openapi.yaml); здесь только соглашения, которые в нём не видны.
Решения A-01, A-05…A-09 — в [spec 005](../specs/005-api-only-redesign.md).

Документ описывает **целевое** состояние. До конца плана 04 код отличается двумя вещами:
аутентификация — cookie-сессия и CSRF, деньги — `float64`. Пагинация `limit/offset/total`
и конверт ошибок уже соответствуют этому документу (план 02).

## Общие принципы

- API — единственный интерфейс сервиса: клиент один (Android), HTML-интерфейса нет.
- Спецификация пишется до реализации; зарегистрированный роут без описания в `openapi.yaml`
  роняет `make test` (`tests/integration/openapi_coverage_test.go`).
- Stateless: состояние запроса — только bearer-токен, никаких серверных сессий в памяти.

## URL Design

```
https://ffs.shatrov.tech/api/v1/{resource}/{id}/{sub-resource}
```

- Существительные, не глаголы; множественное число для коллекций (`/transactions`).
- Kebab-case для составных имён (`/transactions/bulk-delete`).
- Одна семья на инстанс, поэтому `family_id` в пути не появляется: `/api/v1/transactions`,
  а не `/api/v1/families/{id}/transactions`.

```
GET    /api/v1/transactions       # список с фильтрами
POST   /api/v1/transactions       # создание
GET    /api/v1/transactions/{id}
PUT    /api/v1/transactions/{id}
DELETE /api/v1/transactions/{id}
```

## HTTP методы

| Метод | Назначение | Идемпотентность | Body |
|-------|------------|-----------------|------|
| GET | Получение данных | ✅ | ❌ |
| POST | Создание ресурса | ✅ при клиентском `id` (A-07) | ✅ |
| PUT | Полное обновление | ✅ | ✅ |
| PATCH | Частичное обновление (`is_active`, `role`) | ✅ | ✅ |
| DELETE | Удаление ресурса | ✅ | ❌ |

`POST` для транзакций, бюджетов и категорий принимает необязательный `id` (UUID v4),
сгенерированный клиентом: первый вызов — `201`, повтор с тем же `id` — `200` с существующей
записью. Так ретрай после обрыва сети не создаёт дубль.

## HTTP статус-коды

| Код | Когда |
|---|---|
| 200 | GET, PUT, PATCH; повторный `POST` с известным `id` |
| 201 | Создан новый ресурс |
| 204 | DELETE |
| 400 | Тело не парсится (не валидация — она `422`) |
| 401 | `UNAUTHORIZED` / `INVALID_CREDENTIALS` |
| 403 | `FORBIDDEN` — роль не подходит |
| 404 | `NOT_FOUND` |
| 409 | `SETUP_REQUIRED`, `CURRENCY_LOCKED`, `LAST_ADMIN`, `EMAIL_TAKEN`, `CATEGORY_IN_USE` |
| 422 | `VALIDATION_ERROR` — поля в `error.details` |
| 429 | `RATE_LIMITED` + `Retry-After` |
| 500 | `INTERNAL_ERROR` |

## Формат запросов и ответов

`Content-Type: application/json` в обе стороны; исключения — экспорт отчёта (`text/csv`) и
скачивание бэкапа (`application/octet-stream`).

```json
{
  "data": { },
  "meta": {
    "request_id": "req_abc123",
    "timestamp": "2026-09-04T10:30:00Z",
    "pagination": { "limit": 50, "offset": 0, "total": 150 }
  }
}
```

`meta.pagination` присутствует только в ответах-списках.

### Ошибка — одна форма на весь API (A-08)

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed for request",
    "details": [
      { "field": "amount_minor", "message": "must be greater than 0", "code": "min" }
    ]
  },
  "meta": { "request_id": "req_abc123", "timestamp": "2026-09-04T10:30:00Z" }
}
```

`details` заполняется только при `VALIDATION_ERROR`. Других форм ошибки нет: клиент разбирает
любой не-2xx одним типом.

## Пагинация (A-08)

```
GET /api/v1/transactions?limit=50&offset=100
```

- `limit` — по умолчанию 50, максимум 200; `offset` — от 0.
- Ответ несёт `meta.pagination {limit, offset, total}`, где `total` — число записей под
  фильтром без учёта `limit`/`offset`.
- Ни `page`/`page_size`, ни `links` в ответе нет: клиент считает следующий `offset` сам.
- Сортировка через параметр не настраивается — порядок фиксирован сервером (транзакции по дате
  убыванию).

## Аутентификация и авторизация (A-01)

Непрозрачный bearer-токен, выданный `POST /api/v1/auth/login` (единственная публичная операция):

```
Authorization: Bearer <token>
```

Токен — 32 случайных байта в base64url, в БД хранится только SHA-256. Скользящий срок 30 дней
без активности, абсолютный потолок — 180 дней. Cookie, CSRF-токенов и `SESSION_SECRET` в API
нет: они ушли вместе с веб-интерфейсом.

| Ситуация | Ответ |
|---|---|
| Токена нет, истёк или отозван | `401 UNAUTHORIZED` |
| Неверный email или пароль | `401 INVALID_CREDENTIALS` (ответ одинаков для обоих случаев) |
| Роль не даёт доступа к операции | `403 FORBIDDEN` |
| Логин до `setup` (семьи нет) | `409 SETUP_REQUIRED` |
| Сработал лимитер логина | `429 RATE_LIMITED` + `Retry-After` |

Роли — `admin` и `member` (A-04), обе видят все данные семьи:

- **admin** — `/users`, `/backups`, `PUT /family`, `DELETE /categories/{id}`.
- **admin или member** — категории, транзакции, бюджеты, отчёты, статистика.

Роль читается из БД на каждом запросе, а не из токена: деактивация и понижение действуют сразу.
Автор записи берётся из токена, а не из тела — `user_id` в `POST` игнорируется.

Лимитер стоит только на `POST /auth/login` (A-09): 10 попыток / 5 минут на IP и 20 / час на
email. Общего rate limiting на API нет.

## Версионирование

Префикс `/api/v1` фиксирован. Сервер и клиент выпускаются вместе, поэтому двух версий
одновременно не бывает: несовместимое изменение — это `v2` с одновременным релизом Android-клиента,
а `v1` в тот же момент исчезает. Совместимые изменения (новое необязательное поле, новый роут)
идут без смены версии; клиент обязан игнорировать незнакомые поля.

## Соглашения по именованию

- Поля — `snake_case`.
- **Деньги** (A-05): целые в минимальных единицах валюты семьи, поле с суффиксом `_minor`
  (`amount_minor`, `spent_minor`, `remaining_minor`), тип `integer/int64`. Валюта — у семьи
  (ISO 4217), в каждой сумме не повторяется. Проценты и утилизация — `float64`.
- **Дата операции** (A-06): календарная `YYYY-MM-DD` (`format: date`), без времени и зоны.
- **Служебные метки**: RFC3339 UTC (`created_at`, `updated_at`, `expires_at`).
- «Сегодня» и границы периодов считаются в часовом поясе семьи (`family.timezone`, IANA).
- `id` — UUID v4 строкой, без префиксов вида `fam_`.

```json
{
  "id": "0b7f1f2c-4e63-4a09-9b1e-2c1c0a5d9f10",
  "amount_minor": 129900,
  "date": "2026-09-04",
  "created_at": "2026-09-04T10:30:00Z",
  "is_active": true
}
```

## Фильтрация

```
GET /api/v1/transactions?category_id=…&type=expense&date_from=2026-01-01&amount_to_minor=500000
```

Суффиксы `_from` / `_to` для диапазонов (включительно), точное равенство для остального,
`description` — подстрочный поиск. Полнотекстового поиска нет. Точный список параметров каждой
операции — в `openapi.yaml`.

## Мониторинг и логирование

Каждый ответ несёт `X-Request-ID`; то же значение возвращается в `meta.request_id` и попадает в
структурированный лог сервера — по нему сшивается клиентский отчёт об ошибке с серверной записью.
Если клиент прислал свой `X-Request-ID`, он сохраняется.

```json
{
  "timestamp": "2026-09-04T10:30:00Z",
  "level": "INFO",
  "request_id": "req_abc123",
  "method": "GET",
  "path": "/api/v1/transactions",
  "status": 200,
  "duration_ms": 45,
  "user_id": "0b7f1f2c-4e63-4a09-9b1e-2c1c0a5d9f10"
}
```

## Чек-лист для нового роута

- [ ] Описан в `docs/api/openapi.yaml` с `operationId`, ролью в `description` и ответами 4xx
- [ ] Правильные метод и статус-код; списки — с `limit`/`offset` и `meta.pagination`
- [ ] Ошибки — единой формы, валидация — `422`
- [ ] Деньги в `_minor`, даты операций — `date`
- [ ] Роль проверена middleware, автор взят из токена
- [ ] Unit- и integration-тесты
